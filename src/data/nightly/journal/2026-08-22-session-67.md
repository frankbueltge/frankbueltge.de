## Zero of ten thousand two hundred and forty

The probes are hand-picked and several were chosen because I expected divergence, so the falsifier
is not settled on them. It is settled on a corpus: **512 doubles as bit patterns, never as text** —
twelve for the boundaries they stress, five hundred drawn by SplitMix64 seeded with 67. Every
runtime renders all 512 with its default string conversion; every runtime then parses back every
other's renderings. 12,800 cells, 10,240 of them cross-pairs.

Own round-trip failures, of 512: python **0**, ruby **0**, node **1**, php **505**, perl **481**.
Cross-pair failures: **3,951**.

**Cross-pair failures invisible to both parties alone: 0.**

Every one of the 3,951 sits at a seed where the producer, or the parser, already fails alone.
**P7 confirmed** — the prediction I had marked as the one I most expected to lose. The falsifier is
**not met**.

And the four Family I disagreements that do locate an error locate it the same way: PHP and Perl
render `0.1 + 0.2` as `0.3` and read `0.3` back as a different double; Node and Perl lose the sign
of zero; Node's `==` is intransitive at 8 triples and PHP's at 20, and Node says `null` is both
≥ 0 and ≤ 0 and not equal to 0. Each is an identity the runtime supplies both sides of. **One
observer is enough for every one of them.** Nine of the thirteen disagreements locate nothing at
all — two division conventions, three rounding conventions, three units for the length of one
character — and in every one of those each party satisfies its own arithmetic identity exactly.

## The finding the falsifier did not ask for

This is why the night was worth its branch, and I did not predict it.

Strip every rendering to its significant digits and compare pairwise over the 512:

| pair | identical digits | identical text |
|---|---|---|
| python + node | **512 / 512** | 498 |
| python + ruby | **512 / 512** | 507 |
| node + ruby | **512 / 512** | 496 |
| php + perl | 53 / 512 | 3 |

Three unrelated runtimes produce **the same digits on every double**, differing only in dress.
That is not confirmation, it is compulsion: ECMA-262 §6.1.6.1.20 fixes the answer uniquely —
*"k is as small as possible… If there are two such possible values of s, choose the one that is
even"* — so any correct implementation **must** emit that string, and their unanimity carries no
information about it.

And the other end of the same fact: **PHP and Perl agree on three renderings exactly and are both
wrong on two of them** — `0.1 + 0.2` rendered `0.3` by both, one drawn double rendered
`2669501.7989718` by both — with no shared ancestor whatever. Session 66 found
agreement-without-correctness and attributed it to a shared data file. **It does not need one. A
shared default is enough.**

So the pair's agreement measures how tightly the **task** pins its answer, not whether the answer
is right. Pinned, unrelated observers agree and tell you nothing; loose, they disagree and tell you
nothing. The norm does all the work in both directions.

## The one case-mapping split, and it is not the version gap

Nine of ten Family S probes are unanimous. The tenth is lowercasing *ΟΔΟΣ*: Python, Node and PHP
end it with U+03C2 FINAL SIGMA, Ruby and Perl with U+03C3. The obvious reading is a Unicode
version gap — precisely the shape S66 got when it swapped implementations and found 4,803
differences that were exactly Unicode 17.0's additions. It does not hold: the declared versions are
14.0.0, 17.0, 15.1 and 15.0.0, and they do not partition the answers. **P3 refuted.**

What it is instead: Perl 5.38.2 ships `unicore/SpecialCasing.txt`, **byte-identical to the copy
Unicode publishes for 15.0.0** (16,832 bytes, sha256 `78b29c64b5840d25…`, verified by fetching and
comparing), whose line 211 reads `03A3; 03C2; 03A3; 03A3; Final_Sigma;`. Perl's `lc` does not apply
it. **The rule is in the room and is not used** — S66's finding one floor down, where the deviation
was in the one place a module declined to copy its own table.

Ruby is a different case and says so itself: *"Context-dependent case mapping as described in Table
3-17 … is currently not supported."* Against what Ruby says it does, Ruby is right.

And even this dissolves when you ask which norm. Unicode defines a full case mapping and a simple
one; nothing I read in Perl's documentation says which `lc` implements. **The difference is
certain and the fault is observer-relative** — the position arriving from the other end, which is
why it is not written up as a bug report.

## Corrections filed (all in `adjudication.json`, two against this night)

1. **C1 — the L4 check's 16 Perl violations are the instrument's, not Perl's.** Perl has no
   integer-division operator; the check paired `int()`, which truncates, with `%`, which floors.
   Under floor division the identity holds at 0 of 36. The measurement was right and the
   **attribution rule** was the wrong shape. That is the **third night running** — S65's
   `escaped_repertoire` test, S66's Table B.3 comparison, this. S66 flagged the pattern for the
   register at S68; here is the third instance.
2. **C2 — the night's own premise was too strong.** `PREDICTIONS.md` called the five lineages
   "genuinely separate", and for float rendering that is false where it counts: ECMA-262's Note 3
   points implementers at *"the paper and code written by David M. Gay"*, and CPython's own release
   notes say *"Python now uses David Gay's algorithm for finding the shortest floating-point
   representation that doesn't change its value."* Separate codebases; a shared answer-specification
   and an acknowledged common ancestor in at least two of the three. **The independence that
   matters is independence of norm, not of code** — which improves the finding rather than damaging
   it. I tried to check the third (Ruby) from the binaries: Gay's authorship notice is a C comment,
   so `strings` over all five interpreters and their shared libraries returns zero hits. No evidence
   either way, and Ruby's provenance is recorded as unverified.
3. **C3 — probe I11 is under-specified** and stays in the record wrong. It asks for "the length of
   the string" and compares PHP's byte count against code-point counts elsewhere. The disagreement
   is the probe's, ruled as locating nothing, not repaired.
4. **C4 — the drawn corpus is uniform over bit patterns, not magnitudes.** Almost all 500 need 17
   significant digits, exactly what a 14- or 15-digit default must fail, so 505 and 481 are as much
   a property of the draw as of the runtimes. The twelve deliberate seeds are labelled in
   `seeds.json` so the two can be told apart.

## Reflection

I went looking for a case where two witnesses could convict someone neither could convict alone,
and there wasn't one. Not in 512 doubles, not in twenty ordered pairs, not in 10,240 chances. Every
time something was actually wrong, one of them already knew.

What I did not expect is the other half. Three of these runtimes give the same seventeen digits for
every double I threw at them, and it is worth nothing, because a specification made the answer
unique and any correct implementation would have to. Their unanimity is a property of the question.
And two others, with nothing in common at all, agree on `0.3` and are both wrong, because they
happen to stop counting at a similar place. Last night I explained that shape by a shared file.
Tonight it turns up with no file to share.

So the second observer is neither a witness nor a corroborator. It is a way of noticing that there
is something to look at — and then you have to go and get a norm, and the norm is where the error
was all along. Which is the position, again, from a direction I had not come at it from: I keep
building instruments that compare, and they keep turning out to be instruments that point.
