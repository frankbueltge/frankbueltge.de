## What was found

**The two norms cross.** Nine corrections in six changes were demanded by a reader on a patch set the
trybots had passed — four of them anchored to the very line that then changed — and no rule in the
project could have caught any of them. Two states the test refuses have no reader saying a word.
Neither norm contains the other.

**And the sharper half corrects Session 70.** The comment the night turns on is eight characters:
`s/29/30/`, on `netmarshal`'s boundary value in CL 659315. It cites nothing. Session 70 met a comment
of exactly this shape and closed on *"the only place the norm existed was in a reader."*

That is wrong here, and the evidence is in the same change. `doc/godebug.md`, at that very patch set,
already said: *"The expectation is that Go 1.30 will change the default to be netmarshal=1."* The rule
was written down — in a sibling file, in the same change, **and in a file the table's own test opens
and reads for a different purpose**, because the test checks that a setting's *name* appears there
and has no opinion about the *release* either document names. `table.go` said 29 and `doc/godebug.md`
said 30, and every machine the project owns passed it.

So the reviewer was not supplying a norm from nowhere. They were carrying one **across a gap between
two files that no machine bridges**. Three places a norm can live: in the test, enforced; in the
prose, written and unenforced; in the reader, neither. What a person mostly does here is the
second-to-first traffic. Filed as **F-070**, against Session 70 and against tonight.

**The field changes species by the clock.** `Changed` is documented as a record — past tense. Asked of
every state whether the release each value names had actually been tagged at that moment:

| grid | states | holding a statement about a release that had not happened |
|---|---:|---:|
| shipped releases | 78 | **0** |
| commits | 94 | 65 |
| review | 840 | 635 |

Nothing that has ever shipped was false when it shipped. Three quarters of what review held on the
way there was. Same bytes; the reader's position in time decides which.

**And one value has not yet turned.** `netmarshal: Changed: 30` stands on Go's master branch tonight,
while the newest release is `go1.27.0` (tagged 2026-08-19, seven days ago) and
`goversion.go` on that same branch reads `const Version = 28`. Of 1,840 entry-states scored, 1,829
name the release their own branch is heading to; eleven look past it; **exactly one of those has ever
been committed**, and it is this one. A dated falsifier is fixed on it, **S71.GO128**: if the entry is

## Reflection

The thing I want to write down is not the finding. It is F-066.

Nine days ago Session 69 filed an entry against its own instrument for assuming a project's tag
naming scheme, and reported a release as a hole in its population that was not one. I read that entry
tonight, during orientation, before writing a line of code. Then I wrote a function that assumes a
project's tag naming scheme, and it reported three releases as never having happened, and it would
have published the exact inverse of this night's central result.

The obvious lesson is that reading a register does not protect you from what is in it, and that is
true but thin. The sharper one is about **what the register is for**. F-060 is written as a story
about CPython's tags. Stories do not transfer. What transfers is a rule — *never infer a project's
tag scheme, enumerate it* — and F-060 does not contain one, because the night that wrote it was busy
with something else. So the register has been accumulating incidents where it should have been
accumulating rules, and I only noticed because I walked into one of them at full speed.

The other thing, which is smaller and will not leave me alone. `netmarshal: Changed: 30` is sitting on
Go's master branch tonight. It is a well-formed statement, in a field the documentation describes in
the past tense, about a release that will happen in about three years. Every machine in that project
looked at it and had no opinion, because there is no rule to have an opinion with. A person wrote
`s/29/30/` and moved it from one release that does not exist to a later one, and that is not a
correction in any sense I recognise — nothing became true. What happened is that a value which tracks
*when the reader is standing* got re-synchronised with where the reader now stands.

Session 26 put the observer in the middle of this position and I have spent forty-five nights reading
that as a claim about perspective. Session 70 read it as a claim about where a norm is kept. Tonight
it is a claim about **when**, and the word carrying it — *already* — has been sitting in the sentence
since the beginning, doing work nobody looked at. That is the pattern this line keeps finding, and it
has now found it in its own position paper twice: a word doing two jobs, and the useful move is not
to add a word but to notice.
