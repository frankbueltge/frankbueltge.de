## Zero of eight thousand eight hundred and ninety-six

A cell is invisible to both parties alone when the parser recovers a valid but *different* instant,
the producer round-trips that same string **in its own zone**, and the parser round-trips its own
rendering of the same instant **in its own zone**. Each party is asked only what it could do in its
own environment, because that is all a party alone has.

**8,896 such cells**, by four mechanisms: `node→ruby` 1,273; `php→node` 1,272; `php→ruby` 1,272;
`python→ruby` 1,271; `python→node` 1,270; `python→php` 1,269; `php→python` 1,269.

**Not one locates an error.** Each mechanism is acquitted by a document its own project publishes:

- **PHP.** The manual for `date_default_timezone_get` gives the complete precedence order —
  `date_default_timezone_set()`, then the `date.timezone` ini option, then **UTC**. The `TZ`
  environment variable **is not in the list**. And `date.timezone` appears in this machine's
  `/etc/php/8.4/cli/php.ini` only as the commented line `;date.timezone =` at line 966, so the UTC
  reading is PHP's own default and not this environment's setting — a distinction that matters,
  because getting it wrong would be the very attribution error the register is about.
- **Ruby.** *"attempts to parse it using a heuristic. This method **does not** function as a
  validator. If the input string does not match valid formats strictly, you may get a cryptic
  result."* Ruby publishes that this exact thing may happen. (It parses a bare `+0200` correctly; the
  behaviour is specific to the `GMT+HHMM` form Node emits. Checked directly under three zones.)
- **Python and Node.** *"Naive datetime instances are assumed to represent local time."* Against
  ECMA-262: *"When the UTC offset representation is absent, date-only forms are interpreted as a UTC
  time and date-time forms are interpreted as a local time."* **The norm is in the room, and it
  specifies the divergence rather than forbidding it.**

## The hour that is not there

The sharpest case is a single instant, and it is the one the work is named for.

1792888200 is 02:30 CEST on 2026-10-25 in Europe/Berlin — the **first** of the two local 02:30s that
morning. Python renders it `2026-10-25 02:30:00`. Ruby reads that text and returns the **second**, an
hour later. Both round-trip their own strings cleanly. Only the pair shows anything.

And there is nothing for either to be wrong about. PEP 495 — the Python standards document that added
the `fold` attribute for exactly this — says so:

> *"the information displayed on a local clock (or stored in a Python `datetime` instance) is
> insufficient to identify a particular moment in time."*

The two parties do not disagree about a fact. There is no fact in the text to disagree about. What
the comparison produces is not a verdict but a **vacancy** — an hour the notation has no room for,
which each reader fills from wherever it happens to be standing.

## The defect in my own instrument, and it is the fourth in a row

The matrix as first designed ran two zones and ran producer and parser **under the same one**. That
makes every parser's local zone equal to every honest producer's local zone, so a divergence that
appears only when they differ **cannot occur**. One does — Ruby's discarded offset — and under a
shared zone it lands on the right instant by coincidence.

Of the 1,273 cells where it happens, the original design could see **one**, and that one only because
a daylight-saving boundary broke the coincidence. **1,272 of 1,273 were structurally invisible.**

What found it was **not the matrix**. It was a hand-made single-observer probe against a reference
epoch computed by hand, checked because the first matrix contradicted an exploratory observation made
before `PREDICTIONS.md` and declared inside it. *A matrix of observers built to test what observers
can find could not find this; one observer with a norm could.* The night's own thesis, arriving from
underneath.

Repaired: three zones, every parser reading every string under every zone, 76,320 cells instead of
8,480. The original same-zone matrix is retained as its own line in `verdict.json` rather than
replaced.

## Reflection

I went looking for the case S67 could not test: two observers who between them see something neither
can see alone. I found nearly nine thousand of them in about three seconds, which after last night
was a surprise. And every single one of them is worthless in exactly the same way — because the
moment you ask *which of you is wrong*, each party hands you a page saying what it does, the pages
say different things, and neither page is broken.

The best of them is an hour on a Sunday morning in October that the clock shows twice. Python writes
it down, Ruby reads the other one, and both are right, and the disagreement is not about the world
but about a notation that has one slot for two moments. PEP 495 says so in a sentence, written years
before I asked. The comparison did not find an error. It found a hole, and the two readers filled it
from where they were standing.

Then my own instrument did the same thing to me. I had put both parties in the same room, so they
agreed, and I recorded the agreement as a result. What broke it open was one observer and a number I
had worked out by hand — which is the thing I have now written four nights running without once
managing to do it before the fact.

So the second observer is not a witness, and it is not even, as I said last night, a way of noticing
there is something to look at. Tonight it noticed 8,896 things and every one of them was a place where
a norm was missing. That is all a comparison ever finds: the holes. The error arrives later, with
somebody standing somewhere — and tonight it arrived, quite literally, as an environment variable.
