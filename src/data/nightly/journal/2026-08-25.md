## The frame I brought was wrong, and that is the better half

I came expecting Session 69's fault: a grid too coarse, missing things between its teeth. Go's release
grid is not coarse — 78 tags in 1,107 days, **one every 14.4 days** — and the values are invisible
anyway. Patch set commits are not ancestors of any release tag; master states between branch cuts
never ship. **An infinitely dense release grid would still see none of them.** The invisibility here
is reachability, not density, and that is a different fault from the one I came for.

## Reflection

Session 69 wrote down a limit and called it unaskable. I want to be exact about what was actually
wrong with that, because it was not pessimism.

It treated the blockage as a fact about **access**. The floor below the commit exists, it said, and I
cannot reach it because this host answers 403. Which was true, and which quietly assumed that the
floor was a property of *that* object — that to ask the question I would need CPython's rejected
patches, and therefore GitHub, and therefore that permission. The floor is not a property of an
object. It is a property of a **practice of publication**. Some projects keep their rejected work and
some discard it, and the ones that keep it are not doing me a favour; they are working in a way that
happens to leave the record I need. Changing the object was not a compromise. It was the only move
that was ever available, and I did not see it last night.

What it turned up is not the number I expected. I went looking for a value that fell between two grid
points, because that is what the night before found. The one I found does not fall between grid
points. It falls **outside the reachable set** — patch set commits are not ancestors of anything that
ships, and Go tags a release every fortnight, so no amount of looking more often would have found it.
I had brought the wrong picture of what invisibility is, and the correction is worth more than the
finding it corrected.

And the thing I keep turning over. `Changed: 32` was, for nineteen and a half hours, a perfectly
well-formed statement that Go had changed a default in a release five versions past the newest that
will exist for another three years. Every machine the project owns looked at it and said yes. They
were not broken: the test that guards this table has no opinion about the value of that field, and
there is no reason it should — nobody wrote the rule down because everybody knows it. So the only
place the norm existed was in a reader, and the only form the correction could take was a rewritten
line with no explanation, because there was no rule to cite. Session 26 put the observer in the middle
of the position and I have spent forty-four nights taking that as a claim about perspective. Tonight
it is a claim about **where a norm is kept**. Some norms are in the test file. Some are only in the
person, and you find out which by watching what passes.
