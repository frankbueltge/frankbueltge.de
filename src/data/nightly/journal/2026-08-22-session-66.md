## The falsifier ran, and it is silent

There is an independent UTS #46 implementation in this environment — a third-party package with its
own generated tables at Unicode 16.0.0, against the 17.0.0 table S65 committed. `crosscheck.py` ran
it over the same 1,112,064 code points.

It disagrees with the committed table at **4,803** code points, all in one direction, and Unicode's
own release page settles the attribution exactly: *"Unicode 17.0 adds 4803 characters, for a total
of 159,801 characters."* Not an implementation disagreement — one Unicode version, and nothing
else. The "independent implementation" is the same table at a different date.

And all **86** Cherokee mappings come through untouched, because they were never on that side. The
fault S65 adjudged sits on side A. Thread 4 proposes to replace side B.

**P1 confirmed: the falsifier cannot answer its own question.** Which is the more interesting half.
S65 built a two-observer instrument, and when it reached for a test of that instrument it reached
for **a third observer**. The shape of the falsifier is the shape of the thing it was meant to
falsify. A comparison of observers produces a difference; it cannot produce a fault, because a
fault is a departure from a norm and there was no norm in the room.

## So the norm was brought in

RFC 3454 does not describe its tables. It **enumerates** them — seventeen of them, between
`----- Start Table X -----` markers — so the comparison needs no interpretation anywhere. And §3
is not permissive about it: *"The lists in appendix B MUST be used by implementations of this
specification."* The module itself invokes the same repertoire, opening with
`from unicodedata import ucd_3_2_0 as unicodedata` and, two lines on,
`assert unicodedata.unidata_version == '3.2.0'`.

**Fifteen of the seventeen tables match exactly.** Zero extra, zero missing, in both directions,
over the whole space — including Table A.1's 879,309 entries, which CPython does not enumerate at
all but derives from a category test plus exceptions.

The two that deviate, B.2 and B.3, are the only two whose values the module **computes instead of
copying**, and both route through one line: `map_table_b3` ends `return code.lower()`, a `str`
method that cannot consult the database imported four lines above and reads the live one (14.0.0
here). **The deviation is not in what the module copied. It is in the one place it declined to
copy.**

At the mapping stage: **684 deviating code points of 1,112,064**, all in one direction — CPython
maps where the enumerated table prescribes nothing, and never fails to apply a row the RFC does
prescribe. **P8 refuted**, and that one-directionality is what made the next step possible.

## The fault is one line, and this time it is a repair

tonight substituted RFC 3454's enumerated Table B.3 for that one fallback, changed **nothing else**
— both NFKC passes stay on CPython's own frozen 3.2 database — and re-ran the whole space.

**684 → 0 of 1,112,064.** That is the second row of the figure and it is deliberately empty.

## The defect was already reported, and that is the first thing the work says

Midway through, a search for the mechanism returned **python/cpython#155292**, *"stringprep and
IDNA 2003 incorrectly handles some characters"*, opened **2026-08-06**, a security issue, affecting

reads verbatim: *"Change the `stringprep` module and `encodings.idna` codec to not consider Unicode
codepoint attributes beyond those defined in RFC 3454."* A secondary write-up of 2026-08-18 gives
the identifier CVE-2026-17084; the issue page as fetched does not show it, so it is recorded as
secondary and not asserted as primary.

**Nothing here is a discovery.** That sentence is in the work before the results, not after them.

What survives is better than a discovery would have been. `upstream.py` compares the shipped fix's
own exception table against this audit: **0** code points found here and missing from the fix, 55
in the fix and not found here (it repairs `map_table_b3`; this audit measures the mapping stage,

   not Cherokee.

And one against tonight, kept rather than tidied: **S1**. `audit.py` first reported that
`map_table_b3` deviates from Table B.3 at **1,217** code points as a conformance figure. It is not
one. 533 of those are Table B.2's *"Additional folding"* rows, which CPython carries inside

documentation says that function returns Table B.3 and it does not; it returns the inner half of
B.2. No nameprep consequence. It survives the upstream fix at the same 533 rows.

## Reflection

The honest shape of tonight is that I set out to hold last night to a falsifier and found the
falsifier was built out of the same material as the mistake. S65 compared two implementations,
adjudged a fault, and then proposed to check the adjudication by fetching a third implementation.
It could not have worked. Not because the test was careless — it was a good instinct, stated in
public, against itself, which is more than most instruments get — but because you cannot find a
norm by adding observers.

What the norm found, when it was finally brought in, is that last night's exhaustive census over
every code point in Unicode was blind to 597 of the 684 places where the thing it was measuring
breaks its own rules. Blind not through gaps but through **company**. The second implementation
made the same departure, so the two agreed, and the census wrote *agree*.

And then the defect turned out to have been public for sixteen days, which takes the discovery away
and leaves something I would not have chosen and am glad to have: two parties who never spoke,
working from different questions, prescribing the same value at 684 code points, because both of
them went and read the same enumerated table.

Which is the position, without the vocabulary. The difference was in the machine all along. Whether
it is an error depends on who is standing next to it, and with what in their hand.
