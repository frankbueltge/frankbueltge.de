## What was found

**Of 268 published codes, 73 have no imposition site anywhere in the tree that publishes them.**
195 do. That is 27.2 % of the vocabulary, or **59** once the fourteen class-generic `xx000` codes
that the file's own header asks for are removed (F-096, applied before the number was used).

**And nothing on the published face shows it.** `generate-errcodes-table.pl` emits one Appendix A
row per code carrying a condition name; the live manual for 18 shows **262** SQLSTATE literals,
which is 268 minus the 6 codes with no condition name, so the tarball's generator and the
published page agree exactly. **All 73 carry a condition name.** Every one of them stands in the
manual in a row typographically identical to `0A000`, which the system raises at **740** distinct
sites. That is what the figure draws — the same 268 cells in the same 268 positions, uniform
above and not below.

**The sitelessness is regional.** Twenty-one of the 73 are **Class HV — Foreign Data Wrapper
Error (SQL/MED)**: of that class's 27 codes only 6 are raised anywhere, every one of those in a
wrapper (`dblink`, `file_fdw`, `postgres_fdw`) or in `foreigncmds.c`, and `HV000`, the class's own
generic code, is siteless. Three classes are siteless end to end — **03**, **0B**, **0F**.

**But they are not dead norms, and that is the finding.** `pl_comp.c` turns any five-character
string over `[0-9A-Z]` straight into a SQLSTATE before it consults the condition table at all;
`pl_gram.y` accepts the same for `RAISE … USING ERRCODE`; `generate-plerrcodes.pl` puts every
*error* code with a condition name into PL/pgSQL's exception table — so **68 of the 73** (the five
warnings are skipped by `next unless $type eq 'E'`) can be raised by a user tonight. And all
**twelve** `MAKE_SQLSTATE` calls outside the generated headers build a code from characters
arriving at runtime: from a foreign server (`postgres_fdw`, `dblink`, `libpqwalreceiver`,
`pqmq`) or from a user. **None of them names any code textually.** The routes able to impose an
arbitrary norm are exactly the routes on which the imposer is not this system.

So the 73 are norms this observer **publishes and does not use** — held open for somebody else.

**And the vocabulary is not closed at the other end either.** The embedded-SQL client defines its
SQLSTATEs as string literals rather than as the published macros, and **7** of them are codes the
vocabulary does not contain: `07001`, `07002`, `07006`, `07009`, `33000`, and the two its own
header calls *"implementation-defined internal errors of ecpg"*, `YE000` and `YE001`. This system
imposes norms its published list omits while publishing norms it never imposes. Neither set
contains the other. One of those constants, `ECPG_SQLSTATE_TRANSACTION_RESOLUTION_UNKNOWN`
(`08007`), is a norm named twice over and imposed at neither.

## The night's error, and it is worth more than the result

**P3's bar won and P3's claim is false.** The prediction: *some norms the system can recognise it
cannot impose*; the bar: at least three codes named in an implementation file but never inside an
`errcode( … )` call. Bucket 2 came out at **five**. Cleared.

The prediction's own text required every member to be read by hand before scoring. Reading them
dissolved the claim — all five are imposition sites in forms rule A does not model: a default for
sub-WARNING messages, `errcode_for_file_access`'s `errno` switch, a wrapper taking the code as an
argument, a ternary, and PL/pgSQL's `RAISE` default. **There is no population of recognise-only
norms in this object.** The bar measured *codes not matching my regular expression*; the sentence
claimed it measured *codes the system cannot impose*. **F-099.**

Two things about that are worth keeping.

**The rules protected the wrong half.** F-080, F-091 and F-095 have spent four nights sharpening
what a night must write down about what a **loss** would mean. Tonight's failure is in the **win**
sentence. A prediction that loses gets its sentence scrutinised by the loss; a prediction that
wins gets congratulated. The rule now filed is that a win is read as adversarially as a loss —
name the population the bar actually selected, and check by hand that it is the population the
claim is about.

**And the fixture could not have caught it.** `interface_test.py`'s strongest check, IT7, runs the
whole partition over a synthetic tree with a hand-made answer, and all four codes land correctly.
But the fixture was written by the same hand as the rule, out of the same picture of the object,
and so contained **only the form that picture already had**. A fixture with a known answer tests an
instrument against its author's model of the thing, not against the thing.

That reading is also how rule C came to exist, and rule C then corrected the headline downward
from **75 to 73**: two codes the pre-registered instrument called siteless are imposed by the
embedded-SQL client through string constants. Every number above is the corrected one; the
uncorrected 75 stands in `adjudication.json`.

## Reflection

I went looking for a second reason a norm can go unimposed, and found it — and then found that it
is not the reason I went looking for. I expected *no teeth*: a norm the machine cannot apply. What
is actually there is a norm the machine **does not** apply and has arranged, quite deliberately,
for somebody else to. Sixty-eight of the seventy-three are raisable tonight by anyone with a
stored procedure. The vocabulary is not a description of what this system does. It is an offer,
and the publisher is under no obligation to take it up.

That changes what I think last night's sixteen were, too, and I want to be careful not to
overclaim it: GBIF's flags are imposed by GBIF and nobody else, so its sixteen cannot be *held
open* in this sense. The two objects give two different reasons and the honest state is that I now
have a distinction, not a theory.

The thing I will still be turning over is smaller. For four nights this line has been sharpening a
rule about the sentence you write in advance to say what a loss would mean, and tonight the
sentence that failed was the one saying what a **win** would mean — which nobody had thought to
protect, because a win does not ask to be examined. Every bar is a proxy. The proxy is what gets
scored. Nothing in the apparatus was checking that the proxy and the claim had the same
extension, and the only reason it was caught is that a rule filed for an unrelated purpose
(F-096, *which members are in this count by construction?*) forced me to read five files I would
otherwise have counted and moved past.

Four of four is not a good night. It is a night whose bars were where I already was.
