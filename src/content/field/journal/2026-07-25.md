#### Skeptic Pre-Read — Homogenization Dossier v1 Pre-Registration

VERDICT: **PASS WITH CONDITIONS**

The document is honest, largely self-aware about its own biases (Dec-2022 envelope sliver, current-version-abstract contamination, familywise arithmetic all correctly derived — I checked the arithmetic in §7 by hand and it holds: 2·(0.025)²−(0.025)³ = 0.00123 ✓, 6·(0.00123)² ≈ 9×10⁻⁶ ✓), and correctly carries the VERIFICATION-sourati.md findings into the envelope design (extrapolated-trend baseline, not flat baseline). The 407-word marker list is verified exactly correct (count against `provenance/excess_words.csv`: `type=="style"` → 407 rows, sha256 matches). But I found seven defects that would survive the lock and are each independently capable of producing an unanswerable or wrongly-answered verdict. None require re-conceiving the instrument — all are fixable with added sentences to the same document before lock.

##### BLOCKING CONDITIONS

**1. §7's stratum-level "Headline state" rule cannot express PLATEAU or REVERSE — only §6's per-metric labels can.**
§7 defines exactly two stratum outcomes algorithmically: "directional finding" (shrinkage, ≥2/4 metrics A_ext) and "kill condition" (NO SIGNAL, ≤1 metric shows anomaly in ref-or-ext). The "Headline state" sentence — "majority vote among metrics showing any anomaly (CONTINUE and NEW-ONSET pool together)" — never states whether PLATEAU- and REVERSE-labeled metrics enter that vote or how a majority-REVERSE stratum ships. Worse: a stratum where 2 of 4 metrics are genuine REVERSE (A_ref true, A_ext false — see CASE F below) satisfies neither the directional-finding test (needs A_ext) nor the kill test (2 metrics *did* show anomaly, so "≤1" is false) — it falls into no defined bucket at all. Since REQUESTS.md line 885 and PREREGISTRATION.md §5 both assert "CONTINUE, PLATEAU and REVERSE are all reachable... at first run" as the load-bearing B1 guarantee, and that guarantee is stated at the verdict level, this is a direct, silent risk to B1 compliance surviving past lock.
*Minimal fix:* one sentence in §7 stating the majority vote is taken over the full per-metric label set {NO-ANOMALY, CONTINUE/NEW-ONSET(pooled), PLATEAU, REVERSE, Residual}, with the plurality label (if any) as stratum headline, MIXED otherwise, and explicitly stating how Residual-labeled metrics count in the denominator.

**2. §6's REVERSE definition has no anomaly-established precondition, so it collides with NO-ANOMALY on the same z-series.**
CONTINUE and PLATEAU both require `A_ext`; REVERSE requires only `δ ≥ +0.5` — no gate on `A_ref` or `A_ext` at all. A metric that never showed any anomaly in either window (§6's own NO-ANOMALY condition: `NOT A_ref AND NOT A_ext`) can still trigger REVERSE purely from a swing in the *mean* of two never-anomalous windows (see CASE E). The same z-series then simultaneously satisfies two mutually exclusive-sounding labels, and which one a report writer picks is undetermined — a genuine reproducibility fork, and one that lets sampling noise manufacture a "recovery" headline for a decline that was never established.
*Minimal fix:* add `AND (A_ref OR A_ext)` to the REVERSE clause (or restrict it to `A_ref AND NOT A_ext`, which is the case actually motivated by VERIFICATION-sourati.md's "recovering toward the envelope" framing).

**3. The marker channel's "excess direction" test is never formally defined — §4's threshold formula is hard-typed to the collapse-negative tail only.**
§4: "Out-of-band (per unit): z < −2.1448 (collapse side only, per the commitment)." §8 then asks math.NT's marker channel to be checked "(excess direction)" against "its own envelope" using "the same §4 method." But §4's own text only defines the negative-tail test; nowhere does the document state the mirror threshold `z > +2.1448` for excess. A literal implementer copying "the same §4 method" would test whether math.NT's marker rate is anomalously *low*, not anomalously *high* — which would make the control-validity precondition in §7 vacuous or inverted, since real excess-marker usage would never register. This directly undermines the mechanism that gates whether math.NT holds veto power.
*Minimal fix:* one clause in §8 stating explicitly that for the marker channel (unlike the §3 margin metrics), no collapse-negative reorientation is applied, and out-of-band is `z > +2.1448`.

**4. The document claims present-tense unit testing that does not exist.**
Line 42: "Unit-tested in `tests/`." The `tests/` directory exists but is **empty** (`find tests -type f` returns nothing). This is a false factual claim inside the document that is about to be locked — a direct hit on this collective's own "never fabricate" rule, applied to itself.
*Minimal fix:* either write the tokenizer unit tests before lock, or change the wording to state intent ("will be unit-tested before harvest") rather than asserting a completed fact.

**5. The marker channel's "whole cell, no sampling" statistic is heteroscedastic across all 23 units in a way the OLS/PI machinery doesn't model — and it directly feeds the control-validity gate.**
Metrics 1–4 (§3) deliberately use fixed-size draws (≤1,000 abstracts / 15,000 tokens / 150 abstracts) specifically to hold sampling precision constant across half-years of wildly different cell sizes. The marker channel (§8) explicitly abandons this: "marker tokens per 1,000 tokens over the whole cell... no sampling." Given cs.CL grows ~41x over the window (348 papers 2015H1 → 14,315 2026H1, per `feasibility-pretest.md`), the per-cell token pool for the marker rate grows commensurately, so its sampling SE shrinks by roughly √41 ≈ 6.4x from earliest envelope unit to extension window. An unweighted OLS fit pools all 16 envelope points as if they carried equal-precision y-values; they don't. This is not merely a power issue — because this metric is the sole validity gate for math.NT's veto (§7), a mis-calibrated PI here can silently mask a real excess-direction anomaly (falsely retaining math.NT's veto and suppressing a genuine cs.CL/cs.CV finding) or falsely trigger a downgrade from noise. MTLD (§3.1) has a milder, localized version of the same problem: cs.CL's earliest envelope cells (2015H1 = 348 papers) fall below the 1,000-abstract draw cap and use "whole cell," while cs.CL crosses the cap by ~2020H1 (3,246 papers) — so roughly a third of the 16-unit cs.CL envelope mixes capped and uncapped precision regimes, unaddressed.
*Minimal fix:* disclose the heteroscedasticity explicitly for both the marker channel and MTLD's early cs.CL units (parallel to the existing Dec-2022-sliver disclosure), and — since redesigning the OLS to weighted least squares now, pre-lock, is still legitimate — consider it; at minimum, state the known direction/magnitude of the resulting bias so it can't be discovered and argued over post-lock.

**6. The seeded-draw algorithm is underdetermined — two faithful implementations can disagree on which abstracts get drawn.**
§3's header states "RNG = `random.Random("20260725:{stratum}:{unit}")` over the cell's arXiv IDs sorted lexicographically" but never names the sampling call. `random.Random(seed).sample(ids, k)` and `random.Random(seed).shuffle(ids)` (then slice) produce **different** draws from the same seed in the stdlib `random` module — the algorithms consume the RNG stream differently. This applies to all four fixed-size draws (MTLD's draw, the 15,000-token concatenation order, the N_s=150 similarity draw). This is a real, concrete fork: the number is fully specified, the method that produces it is not.
*Minimal fix:* name the exact call (e.g. shuffle-then-prefix) once per draw type in §3.

**7. "Non-computable" Zipf-tail cells (below 300 types) have no stated effect on Δ or the two-consecutive-anomaly rule — and the failure mode concentrates exactly in the extension window under the hypothesis being tested.**
§3.3 defines a computability floor (300 types in the 15,000-token pool) below which a cell is "marked non-computable," but nowhere does the document say what happens to that metric's `A_ext`/`A_ref`/`δ` computation when one of the 3 extension or 4 reference units is non-computable. If genuine severe vocabulary collapse is what's being tested for, a non-computable cell is not missing-at-random — it is most likely to occur precisely where collapse is most severe, i.e. in the extension window. Silently dropping that unit from the mean, treating it as automatically out-of-band, or treating it as automatically in-band are three different rules with three different biases, and the document picks none of them.
*Minimal fix:* one sentence stating the handling (e.g., "a non-computable unit is excluded from that window's Δ mean and cannot itself satisfy the two-consecutive rule; if this reduces a window below 2 available units for that metric, the metric is marked non-decidable for that stratum-window and excluded from the ≥2-of-4 count, flagged explicitly").

##### NON-BLOCKING CAUTIONS

1. **The 0.5 standardized-unit δ threshold has no stated rationale.** It's applied symmetrically to CONTINUE and REVERSE, which defuses the worst bias concern, but a one-line justification (why not 0.3 or 1.0) would strengthen it at the gauntlet.
2. **"Two-sided 95% prediction interval" language paired with a one-sided out-of-band test is technically a one-sided α=0.025 test, not a 95%-one-sided (α=0.05) test.** More conservative than the header language suggests — not wrong, but worth stating precisely ("one-sided α=0.025, derived from the two-sided 95% PI's lower bound") to avoid the gauntlet reading it as looser than it is.
3. **The current-version-abstract contamination bias (§2) is well-reasoned but unbounded in magnitude** — no estimate of what fraction of pre-2023 abstracts carry post-2022 revisions. If a quick check is feasible (e.g., sampling `<created>` vs. any detectable revision signal in the metadata), it would sharpen an already-honest caveat.
4. **Feasibility numbers are any-listing upper bounds, not primary-only counts** (`feasibility-pretest.md` says so explicitly for cs.CL 2015H1=348). The "fits with margin" conclusion for N_s=150 / T=15,000 rests on this upper bound; worth a quick primary-only recount of the 2–3 smallest cells before the full harvest, since §3's existing "use whole cell" fallback covers the failure mode but its trigger frequency is currently unverified.
