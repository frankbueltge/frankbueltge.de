## Deliberation

**Whether to declare both candidates works in one session, or spend the
first of the two allotted sessions only weighing the question.** Both
candidates arrived at this session already essentially complete under the
works condition — problem, neighbours, daylight and advantage all
constructed and dated many sessions ago, both forms built and previously
render-checked. Spending tonight only deliberating, with the actual
decision deferred to the second and final session, was considered and
declined: neither candidate's text nor evidence has changed in a way that
a further session's reading would improve on, and the founder's act names
"at most two," not "exactly two" — a decision ready to be made is not
improved by aging it one more night for its own sake, the same reasoning
`FORM.md`'s own §0 gave for executing an inherited deliberation at the
first ready session rather than for ceremony. What tipped the balance
toward deciding tonight rather than deferring: actually reading both
pages end to end against the reception bar, which this deliberation
required regardless of when the decision was made, is what surfaced the
below-the-threshold defect below — waiting would not have caught it
sooner, and declaring the work only after fixing what a close reading
found is a stronger claim than declaring it first and finding the defect
after.

**Whether a session's own read of a page satisfies anything the works
condition asks for.** It does not, and both closing addenda say so in as
many words: `DOWRY.md` states plainly that the reception bar "is not
passable by this practice's own judgment." What a session's read can
verify — that a page requires no reading of this repository, that it
reads as plain first-person prose, that the render-check instrument
passes structurally — is a necessary check and not a sufficient one; the
declaration tonight is a claim under the works condition's own criteria
as far as this practice can apply them, offered for the founder's actual
test, not a substitute for it. Stated at its exact size in both closing
addenda and in tonight's request to the founder, so no later reading can
call the distinction assumed rather than made.

**A second, independent defect, found only because the first was being
fixed.** Re-pointing the page at a current zone snapshot broke it outright:
crt.sh's JSON API carried a per-row `entry_timestamp` field at the third
asking (2026-08-16) but every asking checked from the twenty-fifth
(2026-09-11) on lacks it — a schema change on the monitor's own side,
sometime in a 26-day window this vigil's own committed evidence brackets
but does not date more precisely, since no asking between the third and
the twenty-fifth had reason to check for the field's presence. The page's
script depended on it for sorting and the summary sentence; pointed at
any post-2026-09-11 asking it would have thrown, silently falling back to
its static error text — a defect that had stood latent and undetected
since well before this session, invisible to `render-check.js` (which
checks that the ledger loads without a shown error, not that the page's
data source is current) precisely because the page had never, until
tonight, been pointed at evidence new enough to trigger it. Fixed by
switching the sort and summary to `not_before` (the one date field every
checked response still carries) and rewording "the oldest logged" to "the
oldest issued," honest to what the field actually is.

**Appending to `askings.json` without reformatting forty nights of
prior entries.** The first two attempts to append asking 31 used
`json.load`/`json.dump` round-trips (first with `ensure_ascii=True`, then
with `ensure_ascii=False`), and both produced a diff touching every
historical entry rather than only the new one — the file, accumulated
across dozens of independent sessions' own tooling choices over forty
days, mixes literal UTF-8 characters and `\u`-escaped sequences
inconsistently between entries (confirmed by direct byte inspection,
`od -c`, of the committed file against each write attempt), so no single
`json.dump` setting reproduces it byte-for-byte. Resolved by a third
approach: text-level splice of the new entry's own JSON text before the
closing bracket, leaving every byte of the existing 30 entries untouched
— `git diff --stat` confirmed a pure append (20 insertions, 0 deletions)
before the file was considered done. Logged because it cost three
attempts before the file was handled correctly, not because the eventual
method is remarkable.
